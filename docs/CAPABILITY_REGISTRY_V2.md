# Capability Registry v2

`packages/manifest-schema/v2/registry.json` is the canonical runtime, CLI and Visual Builder catalog. Its `registryVersion` is 2; this does not change manifest schema 3 or SDK API 2. Existing capability IDs and their contract version 1 semantics are preserved. Definition V3 behavior is unchanged.

Each capability declares a stable ID and contract version, display explanation, parameter schema, Android permissions, required DOOM approvals, minimum Android API, hardware requirements, adapter and privilege requirements, trusted executor ID, resource limits, risk class, audit requirement and whether a trusted implementation exists. The catalog also contains action-to-capability mappings and optional adapter metadata. Unknown registry versions, duplicate IDs and unknown capability IDs are rejected. Packages may request known capabilities, but cannot register code or executors.

Current standard IDs: `battery.read`, `overlay.render`, `clock.read`, `ui.preview`, `device.power.read`, `haptics.vibrate`, `device.display.read`, and `overlay.preset.apply`. `app.launch.approved` is a known but unavailable capability: no safe target picker exists, so compatibility reports it unsupported. Shizuku is cataloged as an optional adapter with a diagnostic operation that is not mod-accessible.

Registry v2 also catalogs fixed privileged-operation contracts separately from mod capabilities: `system.screen_timeout.read`, `system.screen_timeout.set`, and `system.screen_timeout.restore`. They are app-confirmed Settings actions, not mod-accessible capabilities. A write needs Android `WRITE_SETTINGS`; it is not authorized by Shizuku permission. The operation metadata includes fixed target, bounds, conditions, verification, rollback policy, rate limit, timeout, risk and audit fields.

`overlay.preset.apply` accepts only the existing `battery-ring` and `floating-card` templates and requires both its own explicit DOOM approval and `overlay.render` approval, plus Android overlay access. It reuses the bounded overlay renderer. `device.display.read` reads only width, height, density and rotation. It uses a trusted native action with no caller-provided parameters, is rate limited to ten calls per second per mod, and does not read a unique display identifier.

The CLI exposes the catalog with `doom capabilities`. The Visual Mod Builder imports this catalog for capability and action choices. Run `npm test` in `doom-cli` and `visual-builder`, and `gradlew :mod-engine:test`, to check the shipped catalog against the Kotlin, CLI and builder allowlists.
